# Backend V1 — plan d'implémentation

**Objectif :** livrer une API FastAPI PostgreSQL fonctionnelle couvrant la V1, utilisable par un frontend React grâce aux contrats OpenAPI.

**Spécification :** `docs/superpowers/specs/2026-10-09-lsoc-management-design.md`.

**Exécution :** directement dans le dossier partagé, sans toucher aux métadonnées Git protégées. La demande de réalisation vaut autorisation d'implémentation ; les propositions du document sont retenues par défaut. Python >=3.12 (3.13 disponible ici), SQLAlchemy 2, Alembic, Pydantic 2, PostgreSQL, Ruff et mypy strict. Aucun frontend ni fonctionnalité V2.

## Contrats partagés

- API `/api/v1`, dates avec fuseau, affichage/récurrence Europe/Paris.
- Sessions serveur via cookie HttpOnly ; CSRF par en-tête `X-CSRF-Token` pour les mutations authentifiées.
- Transaction par requête ; verrous PostgreSQL avant calcul des réservations.
- Routes typées, erreurs HTTP explicites, liste filtrable des événements, pagination bornée.
- Tâches persistantes en base, worker séparé, SMTP configurable et Mailpit en développement.

## Points de contrôle

- Chevauchements partiels, limites adjacentes et écritures concurrentes.
- Permissions cumulées, accès privés et suppression sans données personnelles résiduelles.
- Invitations et récupération à usage unique, expiration, révocation des sessions.
- FFVB inexploitable, absence de match, protections locales et suspension.
- Récurrences au changement d'heure, exceptions, demandes devenues obsolètes.

## Journal

Pré-vol : les tâches partagent les modèles SQLAlchemy et la transaction par requête. Les services reçoivent une Session et un acteur ; les routes valident les entrées et appellent les services. Le worker utilise les mêmes services métier. Les migrations figent le schéma indépendamment des modèles applicatifs.


## Résultats et décisions de réalisation

- Les modules partagent les contrats Pydantic, les modèles SQLAlchemy et la transaction par requête. Aucun frontend ni mécanisme d'inscription V2 n'a été ajouté.
- Les propositions de la spécification ont été retenues pour réaliser la V1 ; API/worker/file PostgreSQL, Docker local, même domaine en production, base vide et démonstration facultative ont été confirmés dans les réponses utilisateur.
- Les métadonnées Git protégées n'ont pas été modifiées. Les fichiers applicatifs, dépendances virtuelles, données PostgreSQL et journaux de vérification sont dans le dossier projet. Aucun Docker build/up ni déploiement n'a été exécuté.
- Les lectures PostgreSQL sont en UTC ; les récurrences se calculent en Europe/Paris. Les mutations du planning utilisent un verrou transactionnel de club, puis les gymnases en ordre stable. Ce choix V1 privilégie la cohérence des séries et imports ; il limite le débit d'écritures simultanées.
- Les horaires FFVB se modifient par `kickoff_at` et les marges. Le nombre de terrains configuré d'un match (`match_courts`) est conservé indépendamment de son occupation effective (`courts`). Les paramètres par défaut n'affectent que les nouveaux imports.
- Les courriels sont chiffrés en file avec un secret commun API/worker, puis leur contenu est effacé après livraison. Après huit échecs, une relance admin est disponible. Une livraison SMTP et une validation SQL ne peuvent pas être atomiques : un crash entre les deux peut causer un renvoi avec le même Message-ID.
- Les tests présents ont été conservés ; les nouveaux tests de domaine et de revue ont été autorisés. Deux groupes lancés en parallèle ont partagé une base destructive : ce lancement a été corrigé, puis la suite complète a été vérifiée séquentiellement avec un script qui réinitialise la base dédiée.

### Revue indépendante et corrections

La compétence requesting-code-review a déclenché une revue indépendante en lecture seule. Les neuf constats importants ont été corrigés : purge sous verrou du planning, transitions d'invitation sérialisées et rechargées, récupération FFVB avant mutation de source, vérification des séries sur leur état final, conservation des terrains personnalisés, profils publics séparés des comptes admin, titres de notifications bornés, isolation des erreurs par source et catégorie de tâche, décisions datées/attribuées et historisées. Les régressions ont été observées avant les corrections puis vérifiées avec la suite complète.

Les observations mineures sur pagination SQL, durée des transactions multi-sources et révocation dédiée des invitations ont également été traitées. L'avertissement tiers Starlette/httpx de dépréciation du client de test subsiste ; il ne provoque aucun échec.
